# Building NosoDeck

Three build products in one repo (PRD §5):

| Path | Product | Built with |
|---|---|---|
| `Package.swift`, `Sources/DeckKit`, `Tests/DeckKitTests` | `DeckKit` — shared logic, platform-free | SwiftPM (`swift build` / `swift test`) |
| `apps/NosoDeck` | `NosoDeck` — iPhone app, iOS 17+ | Xcode, project generated by XcodeGen |
| `apps/NosoDeckMac` | `NosoDeck for Mac` — menu-bar agent, macOS 14+ | Xcode, project generated by XcodeGen |

There is no CI. Verification is the owner's Xcode pass at each milestone boundary,
tracked in `docs/VERIFY.md` (D12).

## Prerequisites

- macOS 14+ with Xcode 15+ (Swift 5.10)
- XcodeGen: `brew install xcodegen`

## The shared package

```bash
swift build          # from the repo root
swift test           # the whole DeckKit suite; no device or simulator needed
```

DeckKit must not import AppKit, UIKit, SwiftUI, Network, or any other Apple-only
framework — it is the one part of the codebase that can be tested away from a Mac, and
that only holds as long as it stays portable. Platform glue belongs in the app targets.

## The app targets

`.xcodeproj` bundles are **generated output and are not committed**. The committed
`project.yml` specs are the source of truth, which keeps build configuration
merge-friendly and editable as text.

```bash
cd apps/NosoDeck    && xcodegen && open NosoDeck.xcodeproj
cd apps/NosoDeckMac && xcodegen && open NosoDeckMac.xcodeproj
```

Re-run `xcodegen` after any `project.yml` change, and after adding source files if the
project is already open.

Each spec also generates its `Info.plist` (and, for the Mac agent, its `.entitlements`)
from the `info:` / `entitlements:` blocks — so those files are generated too, and are
gitignored. Edit the properties in `project.yml`, never the generated files.

### Signing

`DEVELOPMENT_TEAM` is deliberately absent from both specs so they stay owner-agnostic.
Select your team in Xcode's Signing & Capabilities tab, or add a local (gitignored)
`.xcconfig`. The bundle-ID root `com.noso.nosodeck` is a placeholder until the owner
confirms their developer-account domain (PRD §8); it needs settling before M9, not
before then.

## Working in the Linux container

The agent's container has **no Swift toolchain**, and `download.swift.org` is blocked
by the environment's egress policy, so one cannot be installed. Consequences and the
resulting verification plan are recorded at the top of `docs/VERIFY.md`. In short:
Swift written in the container is unverified until you compile it, and `swift test` on
your Mac is the cheapest, highest-value check at every milestone boundary.

One check does run there, and is worth running anywhere:

```bash
python3 -m venv .venv
.venv/bin/pip install tree-sitter tree-sitter-language-pack
.venv/bin/python scripts/swift-syntax-check.py .
```

It parses every Swift file with a real Swift grammar and exits non-zero on a syntax
error. It is not a compiler — no types, no name resolution — so a clean run means the
files are well-formed Swift, not that they build.
